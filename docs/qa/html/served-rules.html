Address in, rules out

How a user gets the planning rules for one property. Traced from code at commit a6d2e378 (24 Oct 2026).

A user types an address. The app first works out the facts about that lot, such as its zone, council, precinct and heritage status, by asking the NSW government's own planning and map services. It then runs one database query per rule layer and returns only the rules that apply to that lot, each with the council's exact words and page number.

Serving is deterministic: no AI runs at this point. The same address and the same data always give the same answer. The AI work happens earlier, offline, when council documents are read and checked. That is a separate pipeline.

Known weak points (for the review)

  • The main rules route is one 1,663-line file, more than 3 times the project's 500-line limit. Request handling, query building and result shaping all live in that one file.
  • One other route calls this route over HTTP on its own server, instead of sharing a function.
  • Its SQL is assembled by hand, so the review must confirm every value is passed as a parameter.
