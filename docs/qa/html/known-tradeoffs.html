Known trade-offs

Deliberate shortcuts in a solo-built, live system. Draft for the owner to confirm. Commit a6d2e378.

Every system built by one person has shortcuts. What matters is whether they were chosen knowingly and are contained. Each item below names the shortcut, why it was taken, and what stops it causing harm.

ShortcutWhyHow it is contained
One live database, no test copySolo developer, costBackup before every write, guarded queries, explicit approval
No GitHub branch protectionThe free plan blocks itA merge-check script, plus an alarm if main goes red
Build servers run on the developer's PCNo paid runnersRestart script; a stuck check means the PC side is down
Tests run in CI, not before each pushPushes were too slowA merge needs a passing CI run
AI reads council PDFsThousands of pages, no other practical wayEvery rule must match the PDF text and page before it is served; the review queue is never auto-approved
Many one-off repair scriptsA year of data repair workNot on the serving path; reviewed as tooling
Old database password in git historyEarly mistakePassword rotated 22 Oct 2026
Monitor runs on a simple scheduler; a deploy can kill a runSimplest optionNo deploys at 02:00-03:00 UTC; an alarm catches unfinished runs
Data-quality checks are runnable scripts, not ticketsOne source of truthdq_check.py re-runs them all
Major frontend library upgrades deferredRisk to a working appDecision recorded; not re-opened

Open gaps (not deliberate, to be fixed)

GapEvidenceFix
Nothing checks that every clause in a council document was extracted. A page can lose most of its rules and still pass the check. The page check passes a page when only 30% of its rule lines are found (scripts/page_coverage.py:33-37). Real case: City of Sydney section 7.4 lost clauses (b) and (c), and nothing flagged it. Count the clause labels such as (a), (b), 1., 2. in each section of the PDF, and check that each one comes out. Measure how often clauses go missing on a sample first.
